## 1. Purpose and status

Chunk 15 replaces the storage and ownership model of the standard data structures. The ~21 families in `compiler/stdlib/data_structures` were built on one model: every value of a family allocates its nodes from one application-lifetime arena per family, obtained from `canonical_arena_lookup`, and that arena is never freed. Decision Q2 (a) of 2026-10-22 kept that model. Q13 and Q14 of 2026-10-23 need structure copies that can be freed, and Lee is dissatisfied with the model as a whole. Chunk 4 stage 2 (the structure handle type `arena(L, S)`) waits on this chunk. *[2026-10-24: `arena(L, S)` is not introduced (section 2A, decision 12); stage 2 becomes the removal of the region field from the stdlib records (decision 13).]*

This document records what the redesign must satisfy and the question it has to answer. Up to 2026-10-23 it picked no answer; on 2026-10-24 Lee chose the direction recorded in section 2A.

R1.1. Q12 (how to send a version one also keeps) was withdrawn on 2026-10-22 because under Q2 (a) a version is a copyable handle. If the redesign changes what a version is, the question it answered may return; that is part of section 5.

R1.2. *[Resolved 2026-10-24: Q2 (a) is superseded and Q13 withdrawn; see section 2A.]* **Q2 (a) against Q13 and Q14.** Q2 (a) says structure memory is never freed. Q13 produces a copy on every read of an inner structure, and Q14 produces a copy per child start that "is released when the child dies". A copy that is released cannot live in a never-freed arena. The redesign must resolve this. The design document §15 Q14 lists the options Lee has so far not chosen between: an exception to Q2 (a) for structures that must be freed, or a different storage model.

**R2. Functional design stays.** The structures remain functional, as their design documents describe: persistent, immutable versions; an update returns a new version.

**R3. Reuse, and the old version survives.** An update or addition REUSES the elements (nodes) of the old structure in the new one; it does not copy them. The old structure is NOT destroyed by the update.

**R4. Sendable: messages copy by default, move on request; function calls move.** (Lee, 2026-10-23, "option C", design Q18; this replaces the earlier "by move, not copied, not shared" for messages.) **Amended 2026-10-24 (chunk 15 direction, decisions 6 and 7): the copy goes into a buffer attached to the mailbox entry, and an explicit `move` still copies; see the notes below.**
A send (cast, call message, reply, spawn state) COPIES its value by default, for data structures and owned regions; the sender keeps its data. A value the code explicitly marks for moving is transferred in O(1) and the sender may not use it afterwards (E2301 applies only to explicitly moved values). *[Superseded in part 2026-10-24: an explicitly moved value is copied to the receiver as well; `move` only ends the sender's use, so the sender's frame releases it at once. E2301 stays.]* Function calls are not changed: they still MOVE.
The explicit move is spelled `move` (Lee, 2026-10-23: decided). The compiler's legacy `move` builtin (an old actor-migration alias; migration is `migrate_actor`) is being removed, so there is no collision.

R4.1 **How the copy works** (recommended, accepted as part of C; the design direction). *[Amended 2026-10-24: the "fresh owned region" below is renamed a mailbox buffer, attached to the mailbox entry and released at dispatch end unless a part is kept, in which case that part is evacuated to the actor's stack base. "That region then moves to the receiver" becomes "the receiver reads it in place". Q16's move into state is amended accordingly. Owned regions fold into the stack (decision 5), so R4.1 is revisited for them; see section 7.4. The type-directed walk and the per-message table (R4.2) stay.]* The sender copies the message into a fresh owned region, and that region then moves to the receiver. The decided machinery therefore applies unchanged: the dispatch-scoped message region dropped at behaviour return unless moved into state (design §18.7, the SD-7 work stays valid), Q16 move into state, Q17 failed-send release, the mailbox drain. Copying is type-directed: tree-shaped parts are walked with no bookkeeping; a per-message table (source node address to copy) is kept only where the type allows sharing. A raw owned region is copied by traversal from the message's typed roots, not by memcpy, because it holds internal pointers. A later optimisation, only if measured to be needed: in-place forwarding with an undo log (valid because the sender's data is private and the sender does the copy; it needs a spare word or bit per node, which the boxed one-word-per-field record layout may not have, and it cannot write read-only constants).

R4.2 **Sharing is preserved** across every value in one message, including two versions of a structure sent together (Lee, 2026-10-23: yes). One node in the source is one node in the copy. The per-message table is therefore required wherever the type allows sharing. This also answers whether `copy_to` preserves internal sharing for messages.

R4.3 **Evacuation under candidate D** (return from a frame, copy into state at dispatch end). *[Chosen 2026-10-24 as the return mechanism for all escaping values, section 2A decision 2.]* The source frame is dying, so forwarding pointers may be written into it and no table is needed; sharing is still preserved. Non-tail recursion would copy a returned version once per frame (quadratic). The direction is destination-passing: build directly where the result is kept, as region passing does, when the compiler can see the value flows to the return; evacuation otherwise. Lee's cleanup-on-pop rule is unchanged.

## 2A. Chunk 15 direction (Lee, 2026-10-24)

Lee chose this direction on 2026-10-24. It is the chosen basis of candidate (D) in section 4, extended from structures to every escaping value. The detailed design is not written. Where an earlier decision conflicts, the earlier decision carries a dated note in place (Q rows in section 2, R1.2, R4, R4.1, R4.3, section 4); nothing earlier was deleted, and decisions this direction does not touch stand (Q7 to Q10, Q12 withdrawn, Q19, R1 intro, R2, R3, R4.2, R4.3's destination-passing and Lee's cleanup-on-pop rule). Decisions 15 to 17, added in a second pass the same day, supersede Q3, Q4, Q5 and Q11 and retire E2307. Decisions 18 to 21 specify the release mechanism of decision 4. Decisions 22 to 25 settle the error codes. Decisions 26 to 29 settle the stack mechanics. Decisions 30 to 33 settle messages and replies. Decisions 34 to 37 settle explicit regions, ref cells, FFI retention and the carried-over items. Decision 38 closes the last sharing with the sender. Decision 39 splits the failure reasons by cause. Decision 40 lets the programmer choose how the state area gives memory back.

1. **Data structures do not exist in a family allocation. They live in the actors' stacks.** The family arenas (`canonical_arena_lookup`) are removed. Q2 (a) is superseded. Reason: a never-freed arena cannot hold the freeable copies Q14 needs, and Lee is dissatisfied with the model as a whole.
2. **All escaping values are stack-based.** The implicit per-actor heap (section 8.1) is removed entirely: structures, records and tuples returned from functions, list cells, strings and call replies. Returns use the R4.3 mechanism: destination-passing where the compiler sees the value flow to the return, otherwise evacuation on return of only the nodes inside the popped frame; older nodes are left alone, and immutable structures never point from old nodes to new. Lee's rule for returns stands: a version created in a callee's frame and not returned is cleaned up at the pop.
3. **Actor state lives at the base of the actor's stack**, an area the `stack_policy` release algorithms never pop. At dispatch end the new state is evacuated into it, only the nodes built during the dispatch.
4. **Reclamation is completely deterministic and predictable. Nothing similar to garbage collection**: no thresholds, no sweeps, nothing done "every so often". Dead nodes of old state versions at the stack base are released by **compiler-proven release**. Where the compiler proves the old state is dead after the update (its last use, no other live version), the nodes the update replaced are released at once, at a cost proportional to the nodes replaced. Where it cannot prove that, the fallback is to copy the live state into a fresh base area at dispatch end and release the old base area whole, at a cost proportional to the state size (mechanism: decision 28). Which path is taken is decided at compile time, not at run time.
5. **Owned regions fold into the stack.** Explicit owned regions become stack areas; R4.1 and Q16 are revisited accordingly (R4.1 and Q16 carry dated notes; the owned-region part is section 7.4 item 12). Consequence: Q5's per-actor owner lists become unnecessary for this memory, because an actor's end releases its whole stack (first recorded as "for Lee to confirm, not decided"; confirmed by decision 16 below). What releases mailbox buffers still pending when an actor ends stays open (section 7.4 item 20; settled 2026-10-24 by decision 31: the end-of-actor drain).
6. **`move(x)` in a send still copies the data to the receiver.** `move` only means the sender may not use x afterwards (E2301), so the sender's frame can release it at once. There is no O(1) cross-actor transfer. Q18 is amended: copy by default stays; the meaning of the explicit move changes.
7. **Messages wait in a per-message buffer.** The sender copies into a buffer attached to the mailbox entry (today's R4.1 machinery, the fresh region renamed a mailbox buffer). The behaviour reads it there during its dispatch. The buffer is released at dispatch end unless kept; the kept part is evacuated to the stack base. This replaces Q16's "move the region into state" (Q16 amended). Q17's failed-send release applies to the buffer. Sharing preservation (R4.2) stays.
8. **Shared and hardware memory: stack where possible.** Buffers passed to foreign code live on the calling actor's stack, valid for the call only (a buffer the foreign function keeps past the call is declared and lives in the dangerous actor's FFI arena: decision 36). Atomic regions shared between actors (Q7) and device windows stay outside the stack under today's rules.
9. **`main` follows the same stack rules** on its own thread stack; nothing `main` builds goes to a heap.
10. **Q13 is withdrawn.** `get`, and any read of an inner structure, returns the stored inner structure itself with no copy. It is immutable and sits in an older frame or at the stack base; if it ends up in new state, evacuation leaves already-kept nodes alone.
11. **Q14 is confirmed in stack form.** Each start or restart of a supervised child copies the spec's structure into the new child's stack base, at a cost proportional to its size per start. The child's death releases it with the stack.
12. **`arena(L, S)` is not introduced; Q1 is superseded.** `region(L, S)` now means a lifetime-scoped area of the actor's stack in memory space S, released when its frame pops or the message ends, as its lifetime L says. The exceptions kept outside the stack keep their own rules: `region(L, atomic)` shared between actors (Q7) and `device_window`. Reason: with the family arenas gone and owned regions folded into the stack, the two kinds Q1 split (linear owned memory and a non-linear handle to family-arena storage) collapse into one kind, memory with a lifetime on the stack, which `region(L, S)` already names.
13. **Standard data structures need no region field.** A structure is its root reference (`ref?(L, normal, rec)`), its lifetime carried in that type. Updaters allocate new nodes in the current frame, or directly at the destination when the compiler sees where the result is kept, not through `self.region`. Chunk 4 stage 2 therefore becomes: remove the family-arena field from the stdlib records and allocate in the frame. It is a stdlib change with no new type and no rename script.
14. **Actor state stays at the base of the stack and grows downward (2026-10-24).** The stack grows down from its base; the state area is at the base. During a dispatch the state area neither moves nor grows: an update builds its new nodes in the current frames, pointing up into older state nodes, so every pointer from a frame into state stays valid (a call waiting for its reply mid-dispatch keeps its frames, so no evacuation happens before the behaviour returns). Growth happens only at dispatch end, when every frame has been popped: the state area extends downward into the freed frame space, so no live frame can be invalidated. The reservation (machine memory plus swap) bounds it, as it bounds deep recursion. The `stack_policy` release algorithms must decommit only below the state area's current (moving) edge. The alternative of a separate per-actor state reservation was offered and not chosen.
15. **A plain `spawn`'s initial state is copied by the spawner into the new actor's stack base before its first dispatch (2026-10-24)**, the same as a supervised child's spec structure (decision 11).
16. **Stack regions are not linear; safety is by lifetimes only (2026-10-24).** The region checker enforces lifetimes (no reference outlives its frame or the stack base) and isolation. The linear-ownership checks, `drop_owned` and per-actor owner lists are dropped: Q5 is superseded (no longer a consequence to confirm), and Q11 and E2307 are retired. This answers section 7.4 items 16 and 17 and the linearity part of item 12. Item 20 (what releases mailbox buffers still pending when an actor ends) stays open as a mechanism question: the actor's end must release them, but how is undecided. *[Settled later the same day by decision 31: the end-of-actor drain.]* Which error codes stay is recorded in the design document (region_memory_safety_design.md §10).
17. **Q3 and Q4 are superseded (2026-10-24).** They followed from linearity: a callee cannot release its caller's frame (Q3), and reading needs no take-and-return (Q4).
18. **Compiler-proven release (2026-10-24; answers 7.4 item 1).** At dispatch end exactly one thing is live: the new state (sends and replies were copied, frames are gone). "No other live version" is therefore checked within the behaviour only. A per-behaviour use analysis, decided at compile time, proves that the old state and any structure read out of it flow only into updates (not also kept in the new state, captured, or returned another way). Where proven, each update appends the state-area nodes it replaced (its path-copied nodes) to a per-dispatch release log, freed at dispatch end at a cost proportional to the nodes replaced. One kept alias anywhere means no proof, and that behaviour uses the fallback of decision 4.
19. **The fallback is reported (2026-10-24; answers 7.4 item 8).** Where a behaviour cannot be proven, every dispatch end copies its whole live state, at a cost proportional to the state size. The compiler emits a note naming the behaviour and the alias that blocked the proof; a strict mode turns the note into an error. Code numbers and the strict-mode spelling are for the detailed design.
20. **Evacuation via scratch, two copies (2026-10-24; answers 7.4 item 18).** Copy the new nodes reachable from the new state into scratch space below the deepest point the dispatch reached, leaving a forwarding pointer in each source node (safe: those frames are dead, R4.3); then copy the contiguous scratch block up to the state area's edge (or into holes, decision 21), adjusting pointers into it by a constant offset. Cost: two copies of the new nodes, never the whole state. Sliding in place was offered and not chosen.
21. **Exact-size free lists (2026-10-24; answers 7.4 item 19).** One free list per node size in the state area; released nodes go on their size's list; evacuated nodes fill an exact-size hole first and extend the edge only when none is free. Allocate and free are O(1); live nodes never move, so existing pointers are never rewritten. Holes of sizes no longer used are the only waste and are compacted whenever the fallback copy runs. Compaction after release was offered and not chosen.
22. **E2301 stays, as a lifetime error (2026-10-24; answers 7.4 item 23).** `move(x)` means the sender gives x up so its frame can release it at once (decision 6); a later use would read released memory.
23. **E2308 and E2309 are retired (2026-10-24; answers 7.4 item 24).** E2308 lost its reason: the spec is copied into each child's stack base (decisions 11 and 15). E2309 named owned regions, and lifetime conflicts are already E2311.
24. **`device_window` keeps one owner (2026-10-24; answers 7.4 item 25).** Two actors driving one device register block corrupts it ("check when the error corrupts data"); it stays outside the stack with its own single-owner check (spec §4.4.6, H7). No code enforces it today (design H7: the window is not move-only, and the registry names no single-owner code); it needs a code, for the detailed design.
25. **E2300 and E2302 reading confirmed (2026-10-24).** Both are lifetime checks: use of a stack area, or a reference into it, after its frame or area is gone. "Owned binding" means a binding of a lifetime-scoped stack area; "moved out or dropped" means the frame or area is popped.
26. **Sizing (2026-10-24; answers 7.4 item 6).** State and structures count against the actor's existing stack reservation (machine memory plus swap, lowerable per spawn; the board memory budget for the chunk chain on the ESP32-S3). There is no new limit. Hitting the limit during an allocation or evacuation ends the actor with `(:explicit, :stack_exhausted)` under Q9; its supervisor decides. **[Amended 2026-10-24 (decision 39): the reason is split by cause and `:stack_exhausted` is no longer the name for these cases.]**
27. **`stack_policy` (2026-10-24; answers 7.4 item 7).** The state area's edge is one word in the actor control block. Every `stack_policy` release algorithm measures from it instead of from the stack base, keeping its behaviour. The state area is never decommitted while the actor lives. **[Amended 2026-10-24 (decision 40): this holds only under `:keep_state_area`; the programmer chooses how the state area gives memory back.]**
28. **Fallback copy destination (2026-10-24; answers 7.4 item 26).** The scratch technique of decision 20 applied to the whole state: copy the live state into scratch below the dispatch's deepest point, then copy it back to the base with one constant pointer offset, releasing the old base area in place. Two copies of the state; peak memory is about twice the state while copying. The decision 19 note already names the behaviours that pay it.
29. **Strings (2026-10-24; answers 7.4 item 10).** Strings are ordinary escaping values. Each concatenation allocates its exact result length (known when it is built) in the current frame; returning evacuates; keeping in state copies to the base. String literals stay in read-only data and are only pointed to, never copied or released.
30. **Lists are copied on send like everything else (2026-10-24; answers 7.4 item 5).** The type-directed copier gains a List kind; cross-actor sharing of lists (the copier's slice-1 limit, KIND 0 today) ends, because on the stack the sender's frame can pop under the receiver.
31. **Pending mailbox buffers at actor end are released by the end-of-actor drain (2026-10-24; answers 7.4 item 20).** The runtime walks the mailbox queue once and frees each pending buffer, O(pending). The queue is the list; there is no owner list.
32. **Last-use elision is forwarding only (2026-10-24; answers 7.4 item 21).** If the value sent on is wholly a received message's buffer (or a part that owns its own buffer), that buffer is handed on in O(1) without copying; every other send copies.
33. **Replies go into the blocked caller's stack (2026-10-24; answers 7.4 item 22).** The caller is parked at a known point, so the replier copies the reply straight into the caller's stack just below its parked SP; it lives in the caller's frame as the call's result and pops with it. One copy, no reply buffer. A reply that arrives after the caller stopped waiting (the future `call_with_timeout`) is dropped under the call record's lock.
34. **Explicit regions; `copy_to` retired (2026-10-24; answers 7.4 items 3 and 12).** `alloc_region` allocates an area in the current frame (its lifetime is that frame) and follows the same rules as any value: returned means evacuated, kept in state means copied to the base, sent means copied. `copy_to` (Q15) is retired: evacuation and copy-on-send cover every case it served.
35. **Ref cells (2026-10-24; answers 7.4 item 13).** A lifetime check: a cell may only be given a value whose lifetime is at least the cell's (the rule of E2302); a cell in state takes only values that will be in state. Anything else is a compile-time error.
36. **FFI retention is declared (2026-10-24; answers 7.4 item 9).** A wrapper whose foreign function keeps a buffer past the call must say so; such a buffer is allocated in the dangerous actor's existing FFI arena (outside the stack; today `ffi_arena_runtime_asm`, ACB 248 to 264) and released when that actor ends. Undeclared retention is a library bug, contained by the guarded region. The declaration's spelling is for the detailed design and the FFI wrapper specification.
37. **Carried-over items (2026-10-24; answers 7.4 items 14 and 15).** With the family arenas gone, H1 (the shared canonical arena table) closes and no shared mutable allocator state remains at the language level (runtime-internal locks such as the timer table and mailboxes are not language-level). H9 (leaked regions in records and in crashed actors) closes because the stack releases everything. The change-result reshaping (`:unchanged | (:tag, V)`, about 367 updaters, design §3.14) stays in chunk 15, done in the same pass as the stdlib storage rewrite.
38. **Nothing in a message is shared with the sender (2026-10-24).** Every value a send carries is copied (decision 30 for lists). A reference whose `rec` is not bound to an enclosing tuple type cannot reach a send once Q19 is enforced (an unbound `rec` is E2010 everywhere), so every reference in a message has a known layout and is copied. This closes the copier's sharing of unbound refs (KIND 0, WORD) and the "shared with the sender as before" note of design §18.7 item 1.
39. **Failure reasons are split by cause (2026-10-24; amends decision 26).** Stacks grow, so "stack exhausted" is the wrong name. `(:explicit, :reservation_exceeded)` when an actor outgrows a reservation its spawn lowered; `(:explicit, :out_of_memory)` when the default reservation (machine memory plus swap) or, on the board, the memory budget runs out; `(:explicit, :state_too_large)` when the spawner finds that a child's initial state is bigger than the child's reservation (the spawner fails, P11 of the detailed design). `(:explicit, :stack_reserve_failed)` keeps its name: it stays the reason when a stack reservation could not be made at spawn. **Today:** the runtime raises `:stack_exhausted` (guard hit) and `:stack_reserve_failed`; the atoms, the reason-line atom table entries and the affected goldens change in phase 0 of chunk15_stack_memory_design.md §11.1.
40. **The programmer chooses how the state area gives memory back (2026-10-24; amends decision 27).** Decision 27's "the state area is never decommitted while the actor lives" now holds only under `:keep_state_area`. Three choices, all deterministic. `:keep_state_area`: the area stays at its largest size, holes are reused by the free lists (decision 21), nothing is returned until the actor ends. `:shrink_after_compaction`: whenever a fallback copy compacts the state (decisions 19, 28), the state edge moves up to the compacted end and the freed pages are decommitted; proven behaviours never compact, so for them it behaves like `:keep_state_area`. `:compact_on_request`: a builtin the behaviour calls (`compact_state()`) compacts the state and shrinks the area at the end of that dispatch, at a cost proportional to the state's size. **Where:** the choice is a spawn argument, required, with no default (like `stack_policy`, every spawn passes it), separate from `stack_policy`. **Confirmed by Lee 2026-10-24:** the spelling `state_policy(:keep_state_area | :shrink_after_compaction | :compact_on_request)` as the argument after `stack_policy(...)`, and the builtin name `compact_state()`. It applies to every spawning form that takes a `stack_policy` (design §5.4 lists them). A missing argument is a compile error like a missing `stack_policy`.

## 3. How Erlang and the BEAM do it

For comparison only.

- Terms are immutable. Within one process heap, an update builds new cells and shares the unchanged ones with the old term (structural sharing).
- Each process has its own heap with a copying, generational garbage collector. An old version stays alive until nothing reaches it, then the collector reclaims it.
- A message is deep-copied into a heap fragment that the receiver owns. The sender keeps its own copy. Sharing inside the term is not preserved by the copy (a term referencing one subterm twice arrives as two copies).
- A call inside a process passes pointers; nothing is copied.
- Reference-counted binaries over 64 bytes live off-heap and are shared between processes by reference counting.
- ETS copies terms into the table on insert and out of it on lookup.

So the BEAM gets reuse through sharing inside one process and isolation through copying between processes, and it never moves. It needs a garbage collector to know when a shared node is dead. Silica has no garbage collector. Since 2026-10-23 (Q18) Silica's messages copy by default as the BEAM's do, with an explicit move on request, and function calls still move. Unlike the BEAM, a Silica copy preserves sharing inside a message, and the copy goes into a fresh owned region that then moves to the receiver. *[Amended 2026-10-24: the copy goes into a mailbox buffer the receiver reads in place (section 2A, decision 7); nothing moves to the receiver, and an explicit move copies as well.]*

## 4. The central tension

R2, R3 and R4 together:

- R3 says the new version contains nodes of the old version.
- R3 also says the old version stays valid after the update.
- R4 (as first stated) said a send moves the structure. Since 2026-10-23 a send copies by default, so the tension below applies to an EXPLICIT move and to function calls, which still move.

If the sender moves the new version away while still holding the old one, the moved version shares nodes with a version the sender still uses. The nodes cannot be both moved and shared. Either something larger than the one version is moved, or the sender is stopped from keeping the other versions, or the sharing is broken.

Candidate resolutions. *[Updated 2026-10-24: (D) is chosen as the basis, extended to all escaping values (section 2A). (A), (B) and (C) are not chosen; their text is kept as the record.]*

**(A) Move the whole family.** *[Not chosen, 2026-10-24.]* All versions derived from one structure live in one owned region. A send moves the region, with every version in it, in O(1). The old version is intact, but now at the receiver.
- Satisfies: R2 and R3 in full; R4 for an explicit move (moved, O(1)), while a default send copies the family or the version (R4.1); fits the Q5 owner list, Q6 and Q16, since the unit that moves is an owned region.
- Breaks or costs: the sender loses every version of that structure, including old ones it may still want, and its later uses are E2301. The unit of ownership is the whole family, not the version, so a program cannot hand one version away and keep another of the same family. Nothing frees a node inside the region while the region lives, so memory in a long-lived region grows with every update unless some separate reclamation is added (not designed). The region is linear, which interacts with Q11 (see section 5).

**(B) Exclusive ownership at send.** *[Not chosen, 2026-10-24.]* A send is legal only if no other live version shares nodes with the version being sent; the send then moves the nodes.
- Satisfies: R2, R3, R4 for the programs it accepts; reclamation would follow from knowing when a node has no other owner.
- Breaks or costs: knowing "no other live version shares these nodes" needs counting (reference or ownership counts on nodes, or an equivalent). An earlier design (the counted-storage stage, design §17) tried counting and was rejected and removed. Whether it can be checked statically is unknown; the dynamic form costs space and time on every update. For an explicit move, a send that finds sharing would be an error or a copy; which is not decided. (A default send copies in any case, R4.1.)

**(C) Consume the old version on update.** *[Not chosen, 2026-10-24.]* An update takes the old version and returns the new one; the old version can no longer be used.
- Satisfies: R2, R4, and makes ownership simple (one live version per lineage, so a send is plain).
- Breaks: R3's second half, that the old version is not destroyed, and with it persistence as the designs describe it (design §3.14 "A change does not consume its input", and 149 trial updater calls that reuse old versions). Listed because it is the obvious alternative; it contradicts a stated requirement.

**(D) The BEAM pattern with structures kept in the actor's stack.** *[CHOSEN 2026-10-24 as the basis, extended to every escaping value (section 2A). The "Not verified" item at the end of this entry (where actor state lives today) is still not verified; the direction puts state at the base of the stack (section 2A, decision 3).]* Structures live in the actor's stack (per-actor, runtime-managed, released at the message boundary under the `stack_policy` algorithms), not in a heap or family arena.
- Gives: release is free, at a frame pop or the message boundary; no per-structure bookkeeping; no never-freed arena; the returned-record leak (H9) goes away. New versions reuse old nodes inside an actor and the old version stays intact (R2, R3). Q13 falls out: reading an inner structure from state copies it into the working area, as the BEAM does reading ETS *[superseded 2026-10-24: Q13 is withdrawn and the read returns the stored structure, no copy, decision 10]*. Q14 falls out: the spec holds the original, each start copies it into the child's memory, freed at death. No linearity is needed for structures inside one actor.
- Rule for returns (Lee, 2026-10-23): a version created in a callee's frame and not returned before the frame pops is cleaned up. This is the same rule as design §3.3 (an owned value not returned or moved is dropped at scope end), with "moved" meaning "evacuated to the caller".
- Mechanism to record: nodes allocated in the callee frame vanish on the pop. Old versions are safe because immutable structures never point from old nodes to new ones. A RETURNED version is evacuated on return by copying only the nodes whose addresses lie inside the frame being popped, leaving pointers to older nodes (the caller's or the state's) alone. Reuse is kept and the cost is proportional to the new nodes (O(log n) for a persistent update). Intermediate versions unreachable from the result are never copied. The alternative is to allocate in the caller's area, as region passing already does.
- Breaks or open: a stack-resident structure cannot be moved to another actor in O(1), because the stack is one contiguous per-actor reservation. A send therefore copies (decided 2026-10-23, R4: copy by default, sharing preserved, the copy built in a fresh owned region that moves to the receiver). An explicit move of a stack-resident structure needs it built in an owned region. *[Superseded 2026-10-24: an explicit move copies too (decision 6), so nothing needs an owned region for it; the "fresh owned region that moves" above is the mailbox buffer (decision 7).]* Surviving a dispatch into state is a copy, and it must preserve sharing (decided for messages, R4.2; evacuation uses forwarding pointers in the dying frame, R4.3) or a shared structure blows up. Structures must be immutable: a mutable ref cell holding a structure could point into a popped frame, so an E2300-style rule is needed. Stack peak follows the largest dispatch, and `:keep_high_water`-style policies keep it.
- Not verified: where actor state lives today. It is believed to be in the actor control block outside the stack; check this before relying on it.

Combinations or other options may exist. The list above is what had been identified on 2026-10-23, not a proof of completeness.

## 5. Consequences and questions the design must answer

1. **Where does a structure's memory live, and who releases it?** Today: the family arena, never freed. Q13 and Q14 need releasable copies. Q5 releases owned regions by the actor's owner list. The design must say, for each of: a version made by an update, a Q13 read copy, a Q14 start copy, a `copy_to` copy, a structure received by message (a copy by default, R4.1; an original only on an explicit `move`). *[2026-10-24: answered by section 2A: on the actors' stacks; released at frame pops, the message boundary and by compiler-proven release; a received message waits in a mailbox buffer; open: section 7.4.]*
2. **Q5 owner lists.** If structure memory is an owned region, the owner list covers it, and a crashed actor's structures are released. If it is not, say what releases it. *[2026-10-24: consequence of decision 5, confirmed by decision 16: an actor's end releases its stack, so owner lists are dropped; mailbox buffers stay open (7.4 item 20).]*
3. **Q15 `copy_to` and Q16 move into state.** How does a structure interact with `copy_to` (rebuild in the state's region, O(size); sharing is preserved for messages, R4.2)? May a received structure's region move whole into state? Under (A), a received structure is a region, so Q16 applies directly. Under (B), (C) and (D) a received structure arrives as the receiver's copy in a fresh owned region (R4.1) or as an explicitly moved original, so Q16 can apply to that region; how a stack-resident structure (D) does so is open. *[2026-10-24: Q16 is amended (decision 7): a kept part is evacuated from the mailbox buffer to the stack base; `copy_to` is retired (decision 34).]*
4. **Q11.** A linear type may not instantiate a generic parameter. Every stdlib structure is generic in its items. If a structure is, or embeds, an owned (linear) region, then `wbt_map[K, V]` over linear items is rejected, but also the question is whether a structure type itself may be passed through generic code, which the stdlib needs everywhere. The redesign must say how a structure value is typed so that generic stdlib code and Q11 coexist. Not analysed here. *[2026-10-24: structures are no longer owned regions; nothing is linear and Q11 / E2307 are retired (decision 16; 7.4 items 4, 16, 17 answered).]*
5. **Q10.** Lifetime names in structure signatures under implicit quantification: today 9,428 uses of `L` are reported in design §15 Q1; how a structure's lifetime relates to the owned region it lives in is open. *[2026-10-24: a structure is its root reference with its lifetime in that type (decision 13); its relation to the stack region it lives in follows `region(L, S)` as a lifetime-scoped stack area (decision 12).]*
6. **Returned-record leak (H9).** H9 lists owned-region leaks, among them regions inside a record or tuple and regions held by an actor that crashes. This chunk takes it over (ROADMAP row 15).
7. **Change-result reshaping (design §3.14).** Changes return `:unchanged | (:tag, V)` sums, a no-op returns `:unchanged`, and about 367 updaters, about 300 caller sites in `trials/` and 55 in the compiler are affected. Whether the new model changes the result shapes (for example if an update can consume its input under (C)) is open. *[2026-10-24: unchanged; the (C) wording refers to an option not chosen. Decision 37: the reshaping stays in chunk 15, in the same pass as the stdlib storage rewrite; H9 (item 6) closes.]*

(2) Spelling: an explicit `copy_to`-style call, or `get` copying implicitly. Cost: O(size of the inner structure) per read; a loop of reads over a graph is quadratic in the worst case; `has_edge` and `neighbors` need no copy. *[2026-10-24: withdrawn with Q13 (decision 10): `get` returns the stored inner structure, no copy; there is no copy destination or spelling to decide.]*

### 5.1 How the current families store their nodes

*[2026-10-24: this subsection describes TODAY's implementation. The family arena, `canonical_arena_lookup` and the collection value's arena capability are removed by the direction (section 2A decisions 1, 12, 13); the facts about the families' node shapes and sharing stay true.]*

## 8. Source facts (found 2026-10-24)

### 8.1 Where escaping values live today

- Working values are built in stack frames. Values that escape a frame (records and tuples returned from functions, list cells, strings, call replies copied into the caller) are promoted into a per-actor implicit heap: a chain of 64 MB anonymous blocks served by `_silica_rt_region_alloc` and released only when the actor ends (`compiler/design_documents/actor_memory_budget_plan.md`, row "Implicit heap (arena) per actor"; `Phase1_TODOs/actor_stack_growth_plan.md`, "the implicit heap that `region_alloc` served ... is now a chain of 64 MB anonymous blocks").
- This heap was never an explicit decision. It is what remained of the first actor runtime's memory area (commit acf44039a4, 2026-04-07, `_silica_rt_actor_init_region`, "init growable stack region for actor") after chunk 1 (commit 7deb300926, 2026-09-18) moved stacks to their own reservation.
- Standard data structures allocate from process-shared family arenas (`canonical_arena_lookup`, `compiler/src/emitter/apple_silicon_mac/terms/canonical_arena_runtime_asm.silica`: one bump arena per specialization key, never freed before process exit). The stdlib sources that call it are listed in 8.3.
- Q18 copy-on-send is implemented in `compiler/src/emitter/apple_silicon_mac/terms/term_message_copy.silica`: a type-directed copy by descriptor into a fresh owned region, sharing preserved through a per-message table, `move(x)` sending the original, dispatch-scoped release. Under the 2026-10-24 direction `move(x)` copies too (decision 6).
- Actor state: not verified by me where it lives today; the direction puts it at the base of the actor's stack.
